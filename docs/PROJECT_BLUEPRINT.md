# TailerAI v2.0 - Project Blueprint & Implementation Strategy

**Document Status:** **Active** | **Version:** 1.0 | **Date:** June 26, 2025

## 1. Overview

This document operationalizes the best practices for the TailerAI v2.0 project. It serves as the primary technical guide, mapping out requirements, dependencies, potential issues, and the specific strategies we will employ to build a robust, scalable, and maintainable application. This blueprint is based on the `PRD_V2_MASTER_DATASET_ENGINE.md` and the established best practices.

---

## 2. Environment & Dependencies

- **Principle:** Use virtual environments and pin package versions for reproducibility.
- **Implementation:**
    - **Local Development:** A `venv` will be used for local development. To set up: `python3 -m venv venv && source venv/bin/activate`.
    - **Production & Staging:** The environment will be containerized using the project `Dockerfile`. This ensures 100% consistency.
    - **Dependencies:** All Python packages are explicitly listed in `requirements.txt` with pinned versions. Key dependencies include:
        - `fastapi`: Core web framework.
        - `sqlalchemy`: Database ORM.
        - `google-generativeai`: For AI-powered analysis.
        - `python-docx`, `pypdf2`: For resume parsing.
    - **System Dependencies:** `texlive` and its associated packages are installed via `apt-get` within the `Dockerfile`.

- **Potential Issues & Mitigation:**
    - **Issue:** Dependency conflicts.
      - **Mitigation:** Pinning versions in `requirements.txt` prevents this. Regular updates will be managed via pull requests.
    - **Issue:** `texlive` installation is large and slow.
      - **Mitigation:** The `Dockerfile` uses a multi-stage build (if optimized further) and the resulting image is cached, so the installation only runs when the `Dockerfile` changes.

## 3. Version Control (Git)

- **Principle:** Commit early and often with clear messages. Use branches for features.
- **Implementation:**
    - **Branching Strategy:**
        - `main`: Production-ready, deployable code. Merges to `main` are done via Pull Requests only.
        - `develop`: The primary integration branch for new features.
        - `feature/<feature-name>`: Individual branches for each new feature or bugfix (e.g., `feature/latex-engine`, `fix/auth-bug`).
    - **Commit Messages:** We will follow the [Conventional Commits](https://www.conventionalcommits.org/) specification (e.g., `feat:`, `fix:`, `docs:`, `refactor:`).
    - **Rollbacks:** Mistakes will be undone using `git revert <commit>` to maintain a clean history. `git restore` will be used for local, uncommitted changes.

## 4. Code Architecture & Modularity

- **Principle:** Split logical units into separate modules. Define and reuse macros and helper functions.
- **Implementation:**
    - **Python Backend:** The application follows the structure in the `app/` directory:
        - `app/api/routes`: API endpoint definitions.
        - `app/services`: Business logic (e.g., `ContentSelectionService`, `LaTeXEngineService`).
        - `app/models`: SQLAlchemy database models and Pydantic schemas.
        - `app/config`: Application settings.
    - **LaTeX Generation:** This is a critical component.
        - **Modular Content:** Each selected resume item (e.g., a single achievement bullet point) will be passed to the LaTeX engine as a distinct piece of data.
        - **Reusable Macros:** The `mspm_template.tex` will be refactored to use custom LaTeX commands (`\newcommand`) for repeatable elements like section headings, job entries, and bullet points. Example:
          ```latex
          % in template.tex
          \newcommand{\resumeItem}[1]{\item #1}
          
          % Python generates this:
          \resumeItem{Managed a portfolio worth \$650M.}
          ```
        - **Keep-Together Environments:** Each work experience entry will be wrapped in a `tcolorbox` or `minipage` environment to prevent it from being split across pages.

## 5. API Management & Testing

- **Principle:** Document every endpoint and use visual tools for validation.
- **Implementation:**
    - **Auto-Documentation:** FastAPI will automatically generate OpenAPI (Swagger) documentation, available at the `/docs` endpoint in the development environment.
    - **Validation:** Pydantic schemas defined in `app/models/schemas.py` will be used for automatic request and response validation.
    - **Testing:** We will use `httpx` within our `pytest` suite to send requests to our API endpoints during integration tests, validating responses against the defined schemas.

## 6. Error Handling & File I/O

- **Principle:** Gracefully catch and log I/O and parsing errors.
- **Implementation:** A structured error handling strategy will be implemented.

| Error Type                | Trigger                                       | Mitigation Strategy                                                                                             | User Feedback                                     |
| ------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **FileUploadError**       | User uploads wrong file type or oversized file. | FastAPI's `UploadFile` validation will catch this before it hits the service layer.                               | `HTTP 422 Unprocessable Entity` with a clear message. |
| **ParsingError**          | Uploaded PDF/DOCX is corrupted or unreadable. | The parsing functions in `ResumeParserService` will be wrapped in a `try...except` block. The error will be logged. | `HTTP 400 Bad Request`: "Could not parse the uploaded file. Please try another document." |
| **AI_API_Error**          | The Gemini API is down or returns an error.   | The `AI_Service` will have a fallback to a simpler, rule-based keyword scoring algorithm.                         | The process continues, but a warning might be logged. |
| **LaTeXCompilationError** | The selected content contains special characters. | The `LaTeXEngineService` will attempt to auto-correct by escaping characters. If it fails, it will log the error. | `HTTP 500 Internal Server Error`: "Could not generate the PDF. Please review your content for special characters." |

## 7. Automated Builds & Quality Checks (CI/CD)

- **Principle:** Automate the build and test pipeline. Fail fast on broken builds.
- **Implementation:** A GitHub Actions workflow (`.github/workflows/ci.yml`) will be created.
    1.  **On Push to `feature/*`:**
        - Set up Python environment.
        - Install dependencies from `requirements.txt`.
        - Run linter (`flake8`).
        - Run unit and integration tests (`pytest`).
    2.  **On PR to `develop` or `main`:**
        - All previous steps must pass.
        - **PDF Page Count Check:** A dedicated test will generate a sample resume and use `pypdf2` to verify the output is exactly one page. The build will fail if the page count is not 1.
        - (Future) Build and push Docker image to Google Container Registry.
        - (Future) Deploy to Google Cloud Run.

---

## 8. AI Integration

- **Principle:** Secure API keys and handle API errors gracefully.
- **Implementation:**
    - **API Key Security:** The Gemini API key will **never** be hardcoded. It will be loaded from an environment variable, which is populated from a `.env` file locally and from Google Secret Manager in the cloud.
    - **Error Handling:** As defined in the Error Handling section, any failure from the Gemini API will trigger a fallback to a deterministic, rule-based scoring system. This ensures the application remains functional even if the AI service is degraded.

---

## 9. Testing & Validation Strategy

- **Principle:** Write unit tests for business logic and integration tests for end-to-end flows.
- **Implementation:**
    - **Unit Tests (`/tests/unit`):** These will test individual functions in isolation. Examples:
        - Test the relevance scoring algorithm with mock data.
        - Test the LaTeX character escaping function.
    - **Integration Tests (`/tests/integration`):** These will test the interaction between components.
        - Test that a request to the `/optimize` endpoint correctly calls the AI service and stores data in the database.
        - Test the full resume upload, parsing, and storage flow.
